# Face tags in family photos

The existing shared photo viewer now supports face positions. Every uploaded photo opened from the Family Gallery, shared photos, personal albums, weddings, nostalgia, nursery albums, home slideshow or a shared media link uses the same viewer. Thumbnail grids, image dimensions and ordinary tagging controls retain their existing layout.

Detection finds regions containing faces. Names are assigned only by an explicit visitor selection from the existing family-name picker. No identity recognition, face embeddings, age or gender estimates are created. Existing whole-image tags are offered first as choices, never assigned automatically to a face.

Face buttons are invisible until hover, keyboard focus or a tap. Clicking an unlabelled face opens a small search panel beside it, preferring its physical right and clamping to the visible viewport. Only one name/picker can be visible. Desktop names disappear on pointer exit; phone names disappear after three seconds. A named face offers an edit action on touch. Clicking a missed face creates a manual region, which can be adjusted by dragging. The normal photo scroll and touch behavior remains active outside explicit adjustment mode.

Detection runs in an image-only Web Worker on demand, not across thumbnail grids. MediaPipe Tasks Vision 0.10.35 uses the short-range BlazeFace model and overlapping crops for larger group pictures. A local PICO classifier handles browsers without the graphics support required by MediaPipe, or a failed primary model. If automatic detection is unavailable, manual tagging still works. Difficult profiles, small or occluded faces can require manual selection.

The worker accepts network requests only to this site, plus a GET for the exact public MediaPipe runtime URL pinned by SHA-256 integrity. That runtime request omits credentials and referrer information. Photos and detector input pixels are never sent to an external recognition API. The model and CPU fallback are served as static assets. The worker's separate CSP also limits connections. Third-party source, versions, hashes and licences are recorded under `public/assets/vendor/`.

`GET /api/media/<id>/faces` returns small face metadata for one photo. `POST /api/media/<id>/faces/save` creates, updates or clears one face association, using an expected face revision to protect concurrent edits. Rectangles are normalized to the original image, validated and limited to 150 per photo. A label and its ordinary photo tag are written in one transaction. Face edits do not remove unrelated ordinary tags or affect another photo. Clearing a face label preserves the ordinary tag. Ordinary untagging hides the matching face labels; undo restores them. Soft deletion and restoration retain face metadata. Exports include `faceTags` alongside the original media records.

The client keys metadata and detection caches by media ID, cancels abandoned viewer work, avoids re-running detection for recently viewed photos, and reconciles face saves with an ordinary tag request that is already running. Coordinates are projected against the displayed image after resizing, including phone and keyboard-constrained viewports.
