# Face tags in family photos

Desktop photo uploads use this same face picker, detector and resize controls before saving. The upload wizard keeps per-file face drafts in original-image coordinates, maps them through rotation and the final pixel-aligned crop, and submits names, event labels and completion with the original image upload in one database transaction. Cancelling creates no media or new person. Individual upload waits for the destination to confirm saving before removing that draft; failures retain it, and later Upload all excludes already uploaded photos. Remaining non-image files still need explicit batch approval. Family-photo membership and completion controls sit beside the crop/rotate tools; selected people and event labels appear in separate sections below. Next wraps to the first remaining photo.

The viewer's name icon toggles all saved face names above their tagged regions. The age icon independently shows ages beside those regions using the capture date and known birthday; unknown ages are omitted and partial capture dates use the lower whole-year age without an approximation symbol. These display choices reset for another photo and follow zoom, scrolling and tag changes. Names in both the hover bubble and the all-name display link to an existing family profile. Free-name acquaintances and unknown IDs remain plain text. Hover bubbles allow pointer movement onto the name and stay open during keyboard focus. The optional capture-date editor sits near the top of the visual viewport, shrinks above the phone keyboard and scrolls when necessary.

The existing shared photo viewer now supports face positions. Every uploaded photo opened from the Family Gallery, shared photos, personal albums, weddings, nostalgia, nursery albums, home slideshow or a shared media link uses the same viewer. Thumbnail grids, image dimensions and ordinary tagging controls retain their existing layout.

**הצג אזורים מתויגים / Show tagged areas** toggles dashed green frames for all saved face tags in the shared viewer and the desktop upload wizard. Desktop controls include text; phone controls show the icon with an accessible label. With the toggle on, clicking a tagged frame removes exactly that face association immediately through the existing revision-checked dismissal path, with the same update to names, personal-album membership and consecutive numbers. Duplicate occurrences retain their other face tag. Failed writes restore the frame; upload removals only edit the current draft. The toggle survives metadata updates and zooming, and resets on changing or closing the photo. Whole-photo names without saved coordinates remain in the name list.

Phones and installed photo viewers keep **Fit photo** centered above the image, with Previous and Next on either side. The same top group includes the minus/plus controls, labelled **הקטן / הגדל** (Zoom out / Zoom in), and the current zoom percentage. A single horizontally scrollable icon row below the image groups names and tagged regions together, followed by ages/date, tagging completion and albums, editing, download, sharing and deletion. The original controls and listeners are moved rather than copied. Metadata updates, face saves, navigation and keyboard focus retain the row; ordinary desktop browsers and non-photo media restore the original layout. The upload wizard retains its own toolbar.

Detection finds regions containing faces. Names are assigned only by an explicit visitor selection from the existing family-name picker. No identity recognition, face embeddings, age or gender estimates are created. Existing whole-image tags are offered first as choices, never assigned automatically to a face.

Face buttons are invisible until hover, keyboard focus or a tap. Clicking an unlabelled face opens a small search panel beside it, preferring its physical right and clamping to the visible viewport. Only one name/picker can be visible. Desktop names disappear on pointer exit; phone names disappear after three seconds. A named face offers an edit action on touch. Clicking a missed face creates a manual region, which can be adjusted by dragging. The viewer offers 100–800% zoom, scrolling and a fit-photo reset. Face coordinates stay normalized against the original image at every zoom level; a drag scroll cannot create a tag. Manual boxes start at 32 displayed pixels and shrink in original-image coordinates as the user zooms in. Actual face containment takes priority over a nearby expanded touch target, and a broad box cannot swallow smaller independent faces through containment-only deduplication. The normal photo scroll and touch behavior remains active outside explicit adjustment mode.

A coarse detection that spans two independent, supported smaller faces is filtered before publication and again when choosing a face. This prevents a false box around two adjacent back-row heads from capturing both selections. Existing saved face labels are retained. The regression uses the actual normalized regions from the Tomer and Shani wedding photo and checks each selection at phone and enlarged display sizes.

Detection runs in an image-only Web Worker on demand, not across thumbnail grids. Source bitmaps retain up to a 4096-pixel long edge within a 12-megapixel budget, without upscaling low-resolution originals. The primary YuNet 2023mar detector runs with ONNX Runtime Web 1.22.0 in single-threaded CPU/WASM, including browsers without WebGL. Its 640-pixel model input receives the whole photo plus overlapping 1024/384-pixel crops. Fine crops magnify tiny background faces without inventing pixels. Crops containing candidates also receive a horizontally mirrored pass, with eye/mouth landmark ordering mapped back correctly. Strong, anatomically plausible detections at .88 or above stream immediately. Other candidates must pass the additional local verification described below; mirroring a texture alone is insufficient evidence. Landmark-aware suppression keeps overlapping people separate while consolidating repeated predictions. An eight-model-pixel guard at internal crop seams rejects false face slivers; genuine photograph edges remain eligible. Landmark coordinates are ephemeral, stay in the detection worker and are not saved or used for identity matching. MediaPipe Tasks Vision 0.10.35 uses the short-range BlazeFace model with a whole-photo pass and square 1152/512-pixel crops, at least 25% overlap and full edge coverage. Cut-off detections at internal crop seams are discarded in favour of intact boxes from overlapping crops. The model's suppression threshold is .45 to retain nearby overlapping faces. A local PICO classifier scans upright photos at up to 2560 pixels and the other three orientations at up to 1920 pixels with a 16-pixel minimum scan window and .35 clustering IoU. It proposes extra regions for neural verification. If the detailed verifier is unavailable, unverified proposals are not shown as faces and the gallery remains retryable. YuNet does not require the graphics support needed by MediaPipe. Stronger PICO scores are required for supplemental detections. The displayed photo remains unchanged. If automatic detection is unavailable, manual tagging still works. Partly occluded and very small faces are now scanned by the detailed model as well; fully hidden faces or originals lacking sufficient pixels can still require manual selection.

The worker accepts network requests only to this site, plus a GET for the exact public MediaPipe runtime URL pinned by SHA-256 integrity. That runtime request omits credentials and referrer information. Photos and detector input pixels are never sent to an external recognition API. YuNet, its WASM runtime, the MediaPipe model and the PICO fallback are served as static assets. YuNet adds approximately 11.5 MB of lazily loaded, cacheable runtime/model assets only when face detection is requested. The worker's separate CSP also limits connections. Third-party source, versions, hashes and licences are recorded under `public/assets/vendor/`.

`GET /api/media/<id>/faces` returns small face metadata for one photo. `POST /api/media/<id>/faces/save` creates, updates or clears one face association, using an expected face revision to protect concurrent edits. Rectangles are normalized to the original image, validated and limited to 150 per photo. The minimum side is .0005 of the original dimension, allowing precise storage of distant faces smaller than the previous .005 limit. Overlap alone does not reject a second person: duplicate-save checks also require near-identical box centres. Genuine duplicates still reject atomically. A label and its ordinary photo tag are written in one transaction. Face edits do not remove unrelated ordinary tags or affect another photo. Correcting or clearing a face label removes its previous ordinary name tag when no other labelled face in that photo uses that person. Other people and other photos are preserved, and both personal albums are invalidated atomically. Ordinary untagging hides the matching face labels; undo restores them. Soft deletion and restoration retain face metadata. Exports include `faceTags` alongside the original media records.

The client keys metadata and detection caches by media ID, cancels abandoned viewer work, avoids re-running detection for recently viewed photos, and reconciles face saves with an ordinary tag request that is already running. Early detections are displayed while finer scans continue, with stable IDs for repeated boxes. Closing or switching photos terminates an active scan, including safe handling of a bitmap decode that finishes after cancellation. A 90-second worker deadline preserves any useful early results. Coordinates are projected against the displayed image after resizing, including phone and keyboard-constrained viewports.

An open untagged/partial gallery is a stable tagging session. Names and face labels save immediately, but category counts, filtered cards and collection reloads wait until the visitor closes the viewer with X (or another explicit close action). Even a collection request started before opening the viewer cannot apply midway through tagging. Repeated tag, face-scan and review events preserve the active photo and its newest metadata if it is already absent from the registered filtered album. Closing flushes one current collection refresh. Explicit completion instead resets the gallery to `all` immediately without closing its viewer. A retargeted click from a disappearing tag option cannot dismiss the viewer; explicit deletion of the current photo remains available.

## Partially tagged gallery

The Family Gallery offers `all`, `untagged`, `partial`, and `complete` filters over the same media records. An unfinished photo with no ordinary name tags appears only in `untagged`. As soon as it has any ordinary name tag, it appears only in `partial` until the visitor explicitly confirms **All faces tagged**, even if every detected region has a label. Face-position tags are not required. The pending lists never overlap. Zero-tag photos never enter `partial`. Confirmation removes a photo from both pending lists and adds it to `complete`, while retaining it in `all`. The gallery switches to `all` immediately after confirmation, preserving the open viewer even if the photo is absent from the first page. Entering the gallery also defaults to `all`. Classification works before or without a detector scan; detector counts do not decide completion. Old whole-photo tags do not establish which face belongs to a name. The picker offers those existing names for explicit face assignment; no identities are inferred.

Only photos opened from the `partial` gallery receive permanent gold dashed outlines and question badges on unlabelled regions. Saving a face association removes its outline immediately. The collection, counters, search and all pagination pages update after the viewer is explicitly closed. Neither saving names nor confirming completion closes the active photo. Other galleries retain their existing invisible-until-interaction controls.

`gallery-faces.js` scans the entire gallery progressively, one original photo at a time, while the gallery is visible. The queue is independent of the selected page, search and filter. Opening a viewer or hiding/leaving the gallery cancels background work; a viewer scan takes priority. Each completed scan is stored once in `media_face_scans`, with normalized rectangles, detector version and the photo version. Results are shared across visitors; failed or incomplete scans are not recorded as zero-face photos, and failures can be retried. Unknown photos are not assumed complete. The status under the filters shows remaining work. Concurrent results are consolidated instead of allowing a shorter result to erase known regions. Scan metadata is included in exports; edited/restored photo versions invalidate it for a fresh scan, and soft deletion preserves it for undo.

`GET /api/gallery/face-scan?after=<rowid>` provides a bounded cursor batch of unindexed photos and the pending count. `POST /api/media/<id>/faces/detection` validates `{photoRevision, version, faces}` against the current source. `GET /api/media/<id>/faces` also returns saved detection regions, so reopening a photo can draw markers immediately. Saved face labels and ordinary tag changes update the indexed coverage in the same database transaction. Completed scans invalidate collection ETags; different filters have separate cache keys. Timeout/worker-error partial results remain useful in the viewer but are not cached as complete or published as a completed gallery index.

Gallery indexing and visible missing-face markers use the same verified evidence. No secondary-model or cascade-only rectangle is published without the detailed local verifier. If the detailed model is unavailable, gallery evidence remains null rather than recording an unreliable zero-face scan. Existing named face labels remain available and manual tagging still works.

## Verified proposals, duplicates and manual completion

Every uncertain YuNet, MediaPipe or PICO proposal is checked against plausible eye/nose/mouth geometry in local crops at 2.4, 3.4 and 5 times its size. A local score of .88 is sufficient. Otherwise at least two contexts scoring .7 and independent native-pixel PICO support are required. A separate bounded route retains genuine faces of at most 12 original pixels with agreement from two local contexts. Tilted candidates are aligned by their eye axis, or a cascade rotation, and their rectangles and landmarks are projected back onto the original unmodified photograph. A face elsewhere in a proposal's context does not validate the proposal.

Landmark-aware merging consolidates repeat predictions while keeping overlapping people with distinct features. A narrow saved label also covers a larger automatic rectangle when their centres align and the smaller region is substantially contained. This rule is shared by the viewer and stored face coverage. It does not discard another head merely because the boxes overlap. The gallery index version is `gallery-faces-v5`; older scans are replaced progressively and collection ETags include the detector version.


Every gallery photo, including the untagged and partial filters, offers **כל הפרצופים תויגו / All faces tagged**. This stores a durable human completion decision for the current photo and tag revisions; it suppresses unmatched markers and excludes the photo from both pending categories and the automatic scan queue. It does not invent tags or remove the original photo from `all`. The button supports Undo. Editing the photo or changing its tags requires a new confirmation. The write is revision-checked and uses the existing origin/token protections.


Genuine profile proposals with plausible narrow eye/nose geometry have a separate three-context agreement route. High-confidence 13–32 pixel proposals also receive 6×, 8× and 12× contexts, retaining distant heads that become blurry when overmagnified. These routes do not lower the general threshold for flowers, hats, torsos or objects. Tiny faces of at most 12 pixels retain their existing bounded route. Printed photographs can still contain valid face geometry.

An unlabelled region offers **Ignore this detection** and a named region offers **Remove this tag**. Both immediately remove the selected marker and its face label, without a confirmation or an undo-ignore control. The remaining numbered markers and name legend are rebuilt together in a continuous sequence. `POST /api/media/<id>/faces/ignore` stores `{rect, ignored, photoRevision}` in `media_face_ignores`; named removals also send `faceId` and `expectedRevision` to reject stale changes. The selected face association is deleted in the same transaction, and its ordinary name tag and personal-album link are removed only if no other face in that photo retains that person. Removing a duplicated name therefore keeps its other occurrence. Ignored regions are filtered from the viewer, persisted scan output and face counts. Reopening, rescanning, soft deletion and restoring the same photo retain the decision; explicit manual tagging of that position clears its ignored state. A failed write restores the visible marker and reports the error. Edits use a different photo revision, so obsolete coordinates never hide faces in new pixels. Upload drafts use the same dismissal behavior. Exports include `faceIgnores`.

On a desktop with a mouse, selecting a face exposes eight resize handles. Dragging an edge or corner changes the normalized rectangle, including in a zoomed/scrolled image. Named frames save with the same person, face ID and expected face revision. Unnamed frames retain the adjusted rectangle while choosing a name and while later detections stream. Arrow keys adjust a focused handle by one displayed pixel (Shift: ten). Phones retain their existing tagging controls without resize handles.

Wedding and baby albums expose a cover-photo action in their open photo viewer. `POST /api/collections/cover` validates membership and stores the selected media ID in `album_covers`, independently from ordinary person profile pictures. The selected cover persists across uploads and pagination and follows photo edits. If it is deleted, the album uses another available photo; restoring it restores the selection. Exports include `albumCovers`.

For photos, the separate ordinary-tag search and add-name controls are omitted from both the viewer and thumbnail actions. Clicking a face (or manually selecting its location) opens the existing face-name picker. The name chips remain visible and removable; existing whole-photo tags are not migrated, dropped or assigned invented face positions. Face saves continue to write ordinary media tags atomically, so personal albums contain photos with either legacy name tags or new face labels. Video tagging retains its existing name search.
